## 可复核的原故障

从第 15 轮检查点恢复模型、Adam、GradScaler、Python/NumPy/CPU/CUDA 随机状态，重放第 16 轮。原第 116 个 batch 在梯度裁剪处发生同样的非有限范数错误。源检查点 SHA-256 为 `0e041de2cc2e09314457e9c77b3ae870f4d9f95f91fbb267c776580e5bdedaa1`；诊断没有覆盖原检查点。

出错批次的输入、标签、模型参数、优化器状态均为有限数；仅一个参数梯度张量异常。保持该批次、模型和随机状态固定：

| 算法设置 | L1 | 梯度 |
| --- | ---: | --- |
| AMP，scale=131072 | 0.08194210 | 非有限 |
| AMP，scale=65536 | 0.08194210 | 全部有限 |
| AMP，scale=1 | 0.08194210 | 全部有限 |
| FP32，scale=1 | 0.08195911 | 全部有限 |

因此证据支持可恢复的 FP16 缩放溢出，而不是该批次坏图、坏标签或权重已经 NaN。原代码在 `scaler.step/update` 之前用严格裁剪直接抛错，阻止 GradScaler 执行正常跳步和降尺度。[PyTorch 2.7 官方 AMP 示例](https://docs.pytorch.org/docs/2.7/notes/amp_examples.html)说明了非有限梯度时跳过优化器更新及动态调整尺度的机制；本机已安装源码也核对一致。

证据文件：`results/debug_capsicum/replay_legacy.json`、`replay_probe.json`、`replay_fixed.json`、`failing_batch.pt`。诊断脚本放在明确的 `scripts/debug/` 目录，不属于正式模型测试成绩。

## 修复边界和验证

- 检查输入、标签、loss、梯度；只有 loss 有限、启用 AMP 的梯度溢出才交给 GradScaler 跳过参数更新并降尺度。坏梯度不做裁剪或优化器更新。
- 连续超过 3 次或一轮累计超过 8 次溢出停止；整轮没有有效更新也停止。非有限数据/loss、非 AMP 梯度异常继续直接报错。有限梯度仍采用严格范数裁剪，没有全局关闭数值安全检查。
- 日志记录实际成功/跳过步数与尺度。训练平均损失只统计成功更新的样本，并明确记录这一口径。
- 完整重放 161 个 batch 通过：第 116 个 batch 跳过 1 次，其余 160 次更新成功；尺度降为 65536。此为故障轮回归验证，不是最终独立测试。
- 21 项单元/集成检查通过，包括秒级 GPU 溢出恢复、持续溢出不改权重、坏数据不能被恢复机制掩盖、RGB-only/四通道输入语义、下载与配对门禁。
